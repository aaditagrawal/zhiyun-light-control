# Zhiyun Light Control

[![CI](https://github.com/aaditagrawal/zhiyun-light-control/actions/workflows/ci.yml/badge.svg)](https://github.com/aaditagrawal/zhiyun-light-control/actions/workflows/ci.yml)

**Lighttime** controls a ZHIYUN MOLUS G60 from your browser, website, Python,
TypeScript or OBS.

## Why

This project exists as a showcase of long-running autonomous AI engineering:
reverse-engineering an unsupported device, building its SDKs and applications,
and testing the result end to end against real hardware. Agents carry out the
research, implementation, debugging, testing and review; the user supplies the
goals and access to the device.

The original experiment used **GPT‑5.5 xHigh in the Codex app through `/goal`**.
Its starting input was the device's name and a G60 connected over USB to a Mac.
This overhaul uses **GPT‑6.1 Sol through Codex**, with parallel research,
implementation and review. This time the agent had access to Linux instead of
macOS, along with the laptop webcam to verify changes to the physical light.
Analysis, captured replies, automated regressions and real-device
readback inform the implementation.

Subsequent effect exploration, USB analysis and Android enhancements also use
parallel **Claude Opus 5.5** agents, coordinated and physically tested by the
GPT‑6.1 Sol parent.

The repository remains **Zhiyun Light Control**. Python's package, import and
CLI are `lighttime`; the TypeScript package is `@lighttime/sdk`. This replaces
the previous `zhiyun_light_control` / `zlight` implementation; see
[the overhaul and migration notes](docs/overhaul.md).

## Quick start

Turn on the G60, install [uv](https://docs.astral.sh/uv/), then run:

```sh
git clone https://github.com/aaditagrawal/zhiyun-light-control.git
cd zhiyun-light-control
uv run --frozen lighttime
```

Open **http://localhost:8877/**. The bridge discovers and connects a single
nearby G60 (`PL103`) automatically, and the browser attaches to its controls.
No address, token or separate `uv sync` step is needed: `uv run` prepares the
environment using the checkout's Python pin and frozen lockfile. Linux needs
BlueZ running and a powered Bluetooth adapter. Close another app's connection
to the light first. If several G60s are found, use **Choose a light** in the
controller and select yours. The bridge never picks one at random.

## Use it in your website

Point your coding agent at this repository and
[the website integration guide](docs/integrating-sites.md). It includes a
copy-paste agent brief, short SDK/fetch examples and deployment choices.
[AGENTS.md](AGENTS.md) is the operational index for consuming and coding agents.

For a working HTML controller with no JavaScript build step:

```sh
uv run --frozen lighttime serve --web-root examples/site-controller
```

Open **http://localhost:8877/**. This example imports the bridge's
`/lighttime.js` ES module and shares its existing Bluetooth connection.
Serve your own static site the same way, or add the local SDK to an existing
app. A remote app reaches the bridge running beside the light through a
configured private URL or a same-origin proxy; see the integration guide.

## Capabilities and verified limits

- **Brightness and temperature:** 0–100% in whole percentages and 2700–6500 K
  in 100 K steps. Setters return actual device readback. Soft off means zero
  brightness; on restores the session's last nonzero brightness, or 5%.
- **One shared connection:** browser, Python, TypeScript and OBS use the same
  bridge-owned light. [Python](docs/python.md), [TypeScript](docs/typescript.md)
  and [OBS](docs/obs.md) have focused setup guides.
- **Fourteen effects:** fades, breathe, candle/fire, lightning, sunrise,
  heartbeat, Morse and more, generated by the bridge with stop/restore and
  manual override. See [effects](docs/effects.md).
- **Direct clients:** Python BLE and an [Expo Android app](docs/android.md);
  compatible browsers can also use direct Web Bluetooth.

Linux BLE, bridge clients, the browser controller, all fourteen effects and the
OBS HTTP worker were tested on one G60. USB brightness/CCT writes are verified
using Bluetooth readback; pure USB state reads remain unanswered. Other MOLUS
models, Windows/macOS hardware, direct Web Bluetooth, a physical Android run
and an installed OBS UI remain unverified. Camera checks show relative changes,
not calibrated brightness or Kelvin measurements. See
[the validation record](docs/validation.md) and [USB guide](docs/usb.md).

## More ways to run

`lighttime` with no arguments is `lighttime serve`: loopback port 8877,
automatic single-G60 discovery and no bearer-token setup. Use
`serve --address YOUR_BLE_ADDRESS` to choose a device, `--no-auto-connect` to
defer connection, or optional `--auth` for a token-protected bridge. Existing
`--no-auth` invocations remain compatible. See
[Python deployment](docs/python.md) for these flags, a Linux user service and
private HTTPS access.

An optional no-clone invocation is:

```sh
uvx --python 3.14 --from git+https://github.com/aaditagrawal/zhiyun-light-control lighttime
```

This Git install resolves compatible dependencies; it does not reproduce the
checkout's frozen environment. No PyPI, npm or app-store publication has been
performed. For bundled web apps, build and install the local SDK as described
in [the TypeScript guide](docs/typescript.md#install-in-another-project).

## Build and check

Python supports 3.13+; `.python-version` pins the checkout environment. Build
distributions with `uv build --out-dir artifacts/distributions`. For the SDK
and browser, use the manifest-pinned Bun:

```sh
cd packages/sdk
bun install --frozen-lockfile
bun test
bun run typecheck
cd ../..
bun scripts/build-web.ts
```

From the repository root, `bun scripts/build-web.ts` is the canonical web
rebuild: it builds the controller and `/lighttime.js` and copies them into the
Python package's static assets. For Python checks:

```sh
uv run --frozen pytest -q
uv run --frozen ruff check src tests scripts integrations/obs
uv run --frozen ty check
uv audit --frozen
```

[CI](.github/workflows/ci.yml) checks frozen Python 3.13/3.14 environments,
SDK tests/build/types and Android tests/types without hardware.
[`scripts/hardware_verify.py`](scripts/hardware_verify.py) is a separate
physical test that changes the light and can capture camera images.
The Android preview APK uses debug/test signing and has a documented unresolved
Expo CLI dependency advisory; see [Android notes](docs/android.md).

CRC and commands, then compared with captured G60 replies. The SDK is
